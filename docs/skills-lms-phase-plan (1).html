Delivery plan / eight phases

Every phase ends with something an organisation would actually use

No phase delivers a layer. Each one adds a capability that completes a loop, so the product is demoable, pilotable and cancellable at eight different points.

00

Ground rules

  • Vertical slices, not horizontal layers. A phase always includes schema, API and screens for the thing it adds. "Backend for everything, then frontend for everything" produces nine months with nothing to show.
  • Each phase has a demo script. If you cannot walk a stranger through it in five minutes, the phase is not defined yet.
  • Multi-tenancy is in phase one and never revisited. Retrofitting tenant isolation is the most expensive mistake available on this project.
  • Conscious gaps are written down. Every phase lists what is missing and the manual workaround, so a pilot customer hears it from you before they find it.
  • Durations assume a small team: two backend, one frontend, one shared full-stack, design part-time. Adjust proportionally, but phase four does not compress much regardless of headcount.

The arc

P1

Foundation

4–6 weeks · blocks everything · no dependencies

A multi-tenant application organisations can log into, populate with their people, and use to see who knows what.

Data and platform

  • Schema: tenant, person, membership, org_unit with LTREE path, identity_provider
  • Schema: capability, role, role_capability, role_grant
  • Schema: flat skill table plus self_declared_skill
  • Append-only audit_log with no update or delete grants
  • RLS enabled and forced on every tenant-scoped table
  • Connection pool wrapper that sets app.tenant_id before any statement and fails if unset
  • Migration tooling, seed script, two demo tenants
  • CI, staging environment, error tracking, backup and restore drill

Backend

  • Tenant provisioning as a single transaction
  • Email plus magic-link auth; OIDC per tenant behind a flag
  • Session resolving person to memberships, tenant picker when multiple
  • can(actor, capability, resource) v1 with Redis-cached capability sets
  • Member invite, deactivate, bulk CSV import with dry-run diff
  • Org unit CRUD with subtree move and path rewrite
  • Skill CRUD and self-declaration endpoints
  • People search filtered by declared skill and org unit
  • Audit middleware capturing actor, before and after, request id

Frontend

  • App shell: tenant theme from session, top bar showing tenant name, capability-gated navigation
  • Sign in, magic link, tenant picker
  • Member directory with search and filters
  • Org unit tree editor with drag to reparent
  • My profile: declared skills, org unit, manager
  • Admin: roles and grants, member import wizard with diff preview
  • Empty states carrying the next action on every screen
  • Accessibility floor: focus states, keyboard nav, no colour-only status

QA

  • Isolation suite: seed two tenants, run every list endpoint as A, assert zero rows from B
  • Permission matrix tests per role against every endpoint
  • Load a 5,000-member tenant and check directory and tree performance

Shippable as

An internal skills directory. An organisation imports its people, everyone tags what they know, and anyone can find who has done Kubernetes before. That alone gets used.

Conscious gaps. Skills have no levels and nothing is verified, so declared skills are self-reported only and the interface must say so plainly. Workaround: none needed, since a directory is honest about being self-reported.
P2

Skill framework and grades

4–5 weeks · depends on P1

Each organisation defines its own skill levels and career ladder, and every person can see the distance to their next grade.

Data and backend

  • Schema: skill_domain, skill_level with indicators and evidence kinds, skill_edge for prerequisites
  • Schema: tenant_skill_override for copy-on-write on a global library
  • Schema: track, job_profile, profile_requirement, readiness_snapshot
  • Skill versioning: publish creates a new version, never mutates
  • Cycle rejection on prerequisite insert
  • Readiness computation, triggered on change and nightly as a backstop
  • Team rollup queries scoped by org subtree through can()
  • Two or three seeded starter frameworks by industry

Frontend

  • Taxonomy editor as a grid with inline edit, bulk paste, diff and publish
  • Skill page with the five level rubrics as its main content
  • Prerequisite picker showing the upstream graph for that skill only
  • Job profile editor: pick skills, set minimum level and criticality
  • Grade ladder view showing the diff between adjacent grades
  • Learner home rebuilt around the gap to the next grade
  • Manager heatmap: members against core requirements, with a "one gap from promotion" filter

Shippable as

A competency framework tool. An L&D lead builds a forty-skill framework and a four-grade ladder in an afternoon, and every manager sees their team mapped against it.

Conscious gaps. Readiness is computed from self-declared levels, so it is indicative only. Label it "self-reported" everywhere in the interface and resist the urge to put it in a report that leaves the team.
P3

Resources and roadmaps

3–4 weeks · depends on P2

Every gap becomes an ordered plan, with suggested learning from anywhere on the internet.

Data and backend

  • Schema: resource, resource_skill, resource_rating, resource_progress
  • Schema: roadmap, milestone, roadmap_template
  • URL normalisation and dedupe so one link is one record
  • Open Graph metadata fetch for title, duration and provider
  • Generation algorithm: diff, expand intermediate levels, close prerequisites transitively, topological sort, tie-break on effort
  • Milestone locking until prerequisites are satisfied
  • Additive regeneration that never drops a milestone with evidence attached
  • Resource ranking: helpful ratio weighted by raters who later reached the level, then recency, then cost ascending
  • Moderation queue for submitted resources

Frontend

  • Roadmap as a vertical stepper, current milestone expanded, the rest one line each
  • Locked milestones stating why and linking to the blocker
  • Milestone detail: level rubric, accepted evidence, suggested resources
  • Resource list always inside a skill-level context, never a standalone catalog
  • Submit a resource, with duplicate detection before save
  • Explicit "I learned this elsewhere" path that skips the catalog entirely
  • Two-tap rating prompt shown after a level is reached
  • Progress shown as milestones done out of total, never a percentage

Shippable as

A guided development planner. A person picks their next grade and gets an ordered path with real links, and a manager can see who is actively working toward what.

Conscious gaps. Completing a milestone is still self-reported, so nothing in the system is yet trustworthy enough for a promotion decision. Say this out loud in pilot conversations; it sets up phase four as the answer.
P4

Verification loop

6–8 weeks · depends on P2 · the phase that cannot be cut

An organisation nominates who may confirm which skills, and confirmed levels become a separate, trustworthy tier of data.

Permission model

  • Schema: verifier_authority with skill or skill group, max level, org scope, quorum flag, validity window
  • Authority resolution query, indexed for the routing path
  • Conflict rules: not self, no reciprocal pair inside 90 days, optional manager exclusion above a threshold level
  • Separate verifier.grant capability, held only by org admin, with its own audit stream
  • Delegation with a hard expiry

Workflow backend

  • Schema: skill_claim, evidence, verification, skill_assertion
  • State machine: draft, submitted, in review, verified, returned, rejected, expired, revoked
  • Routing on submit, with fan-out to every eligible verifier and claim on open
  • Quorum support: n independent approvals before an assertion is written
  • SLA timers per level, escalation up the authority chain, admin alert on second breach
  • Assertion write as one transaction: compute valid_until, recompute readiness, emit events
  • Revocation path with reason, never a delete
  • Every decision stores the authority row and policy version used
  • Evidence upload to object storage: per-tenant prefix, signed URLs, virus scan, size and type limits
  • Readiness and all reports switched to read verified assertions only

Frontend

  • Claim submission per milestone, showing accepted evidence kinds and what is still missing before submit enables
  • Verifier queue sorted by SLA risk, filterable by skill and team
  • Evidence detail on one page: rubric, all attachments, learner rationale, decision actions
  • Approval requires a score per rubric indicator plus a comment
  • Return path with a specific request for what is missing
  • Authority grant matrix: principals down, skill groups across, max level in the cell
  • Verifier's own mandate visible on their profile
  • Verifier workload panel: pending, median turnaround, signed this quarter
  • Mobile review flow, since leads approve between meetings
  • Verified badge treatment distinct from self-declared everywhere, by shape and text not colour alone

QA and ops

  • Tests proving no path to self-approval, including through delegation and group membership
  • Audit log export for a single claim, readable by a non-engineer
  • Escalation job tested against clock skew and timezones

Shippable as

The actual product. A tech lead confirms a colleague reached Kubernetes L3, the record is dated, attributed and auditable, and the team's capability picture becomes something a director would act on.

Conscious gaps. No certificate to share outside yet, and all evidence is manual, so verifier load is at its highest here. Workaround: start pilots with a narrow skill set, three or four verifiers, and measure turnaround from day one.
P5

Certificates

3–4 weeks · depends on P4

Every verified skill produces a signed credential anyone can check without an account.

Data and backend

  • Schema: issuer_key, credential, status_list
  • KMS integration, one Ed25519 keypair per tenant, private keys never in the database
  • did:web document served from the tenant path
  • Open Badges 3.0 payload builder including criteria, evidence kinds, rubric version, expiry and taxonomy alignment
  • Signing worker on the queue, with retry and a dead-letter path
  • Status list publication for revoked and expired credentials
  • Expiry job driving valid_until, plus recertification claim creation
  • Supersede on renewal, keeping the old credential verifiable and linked
  • Key rotation keeping old public keys resolvable indefinitely

Frontend

  • Public verify page, server-rendered, no auth, fast on mobile
  • Verify page shows the rubric in plain language for an outside reader
  • Signature and status check result stated explicitly, including when it fails
  • Share actions: link, QR, LinkedIn-ready payload, printable certificate
  • Learner wallet listing credentials across every tenant they have belonged to
  • Expiry warnings at 90, 30 and 7 days with a one-tap renewal start
  • Certificate branding per tenant: logo, accent, issuer name

QA

  • Payload validated against an external Open Badges 3.0 validator
  • Revocation reflected on the public page within a minute
  • Verify page load budget under one second cold

Shippable as

A verifiable credentialing platform. Someone leaves the company and keeps a credential their next employer can check, which is the strongest argument you have for learner buy-in.

Conscious gaps. No wallet app integration and no cross-organisation recognition. Both are fine to defer, since the link is what people actually share.
P6

Assessment engine

4–5 weeks · depends on P4

Lower levels become self-serve, which is the only way verifier load stays survivable as a tenant grows.

Data and backend

  • Schema: item_bank, item, attempt, attempt_response, attempt_policy
  • Stratified item draw with a stored seed so an attempt is reproducible for disputes
  • Answers never sent to the client; scoring on submit only
  • Cooldown and quarterly attempt caps enforced server side
  • Per-item exposure counters with automatic retirement above a threshold
  • Per-tenant item subsets drawn from a shared bank, since tenants are competing companies
  • Answer-pattern similarity flags across attempts
  • Auto-attach a passed attempt as evidence on the relevant claim
  • Fast-path policy per level: what light review means for L1 and L2

Frontend

  • Item authoring screen plus CSV import for bulk bank building
  • Attempt runner: one question per screen, timer, autosave, no back navigation
  • Connection loss recovery that resumes rather than voids
  • Result screen showing pass or fail, threshold and domain breakdown, never which items were wrong
  • Cooldown stated as an exact date and time
  • Artifact submission with a written rationale against the rubric
  • Integrity report for admins: exposure, flags, approval anomalies

Shippable as

A self-serve certification path for foundational levels, with human review concentrated where judgement actually matters.

Conscious gaps. No code sandbox, no proctoring, no item response theory. Multiple choice plus artifacts covers most of what an internal framework needs at L1 to L3.
P7

Rewards

3–4 weeks · depends on P4 · optional per tenant

Verified progress pays out, on a ledger finance can audit.

Data and backend

  • Schema: xp_event as single-entry, mint only
  • Schema: reward_account, reward_txn, reward_posting with a zero-sum check constraint per transaction
  • Idempotency key derived from source event and rule id, enforced unique
  • Schema: earning_rule with version, caps and cooldowns; reward_item; redemption
  • Minting only from verified assertions, grade satisfaction, verification work performed and mentoring
  • Blocked-mint queue when the budget pool is empty, surfaced to the admin
  • Redemption as reserve, fulfil, settle, with rollback on vendor failure
  • Reversal transactions on credential revocation
  • Nightly balance snapshot, plus a reconciliation job asserting all accounts sum to zero
  • Anomaly job: reciprocal verifier pairs, sub-minute approvals, outsized shares per verifier

Frontend

  • Wallet: coin balance, XP total, transaction history with every line linked to its cause
  • Catalog leading with non-cash items: conference budget, stretch assignment, assessor status, learning day
  • Redemption flow with a clear reserved state while fulfilment is pending
  • Cohort standing as an opt-in percentile band, with no global leaderboard anywhere
  • XP label configurable per tenant, since game vocabulary does not suit every organisation
  • Admin: earning rule editor with a dry run over the last 30 days of events
  • Admin: burn against budget, outstanding liability, per-person annual redeemed total for payroll

Shippable as

A recognition programme tied to proven capability rather than attendance, with a ledger that survives a finance review.

Conscious gaps. No vendor integrations, so redemption fulfilment is a manual admin action against an order queue. That is genuinely fine for the first several tenants.
P8

Automation and analytics

4–6 weeks · depends on P4 · first scale-oriented phase

The loop runs without an administrator pushing it, and leaders get answers they cannot get anywhere else.

Data and backend

  • Schema: event with a fixed verb vocabulary, backfilled from existing tables
  • Schema: rule, rule_run, notification
  • Rule evaluation in a worker, keyed on event id so replay is idempotent
  • Scheduled triggers: expiry at 90, 30 and 7 days; stalled roadmap after 30 days; weekly verifier digest
  • Fixed action set: assign roadmap, notify, mint reward, grant temporary delegation, flag for review
  • Read replica plus nightly read models for reports
  • The seven MVP reports, each scoped through can()
  • Per-tenant export and hard delete, covering object storage
  • Retention jobs for evidence artifacts
  • Time-boxed platform impersonation with reason, tenant-admin notification and a separate log
  • Load test at 50,000 members in one tenant; query budget review

Frontend

  • Rules list with plain-language summaries readable without opening them
  • Rule editor as a guided form with a dry run reporting who would have been affected
  • Notification preferences per person per kind, with daily batching by default
  • Report screens with org scope selector, date range and CSV export
  • Audit log viewer for admins, filterable by person, claim or action
  • Admin health panel: verifier queue depth, SLA breaches, blocked mints, failed jobs

Shippable as

A platform an organisation can run at scale without your team in the loop, and one that can pass a procurement and privacy review.

C

What to cut first

Assume you will run out of time somewhere around phase five. Cut in this order.

CutCost of cutting
Resource catalog (P3)Low. People already learn elsewhere. Keep the roadmap, drop the curated links and the ratings. If the pilot shows nobody uses it, cut it permanently.
Rewards (P7)Low at first. XP alone is cheap and covers most of the motivational value. Coins can wait for a tenant who asks and funds a budget.
Assessment engine (P6)Medium. Verifiers absorb the load instead, which works for a pilot of 200 people and breaks at 2,000.
Automation (P8)Medium. Admins do it by hand. Painful but survivable while tenant count is small.
Certificates (P5)High. You lose the learner-side reason to care. Cut the wallet and branding, keep a signed verify page.
Verification (P4)Never. Without it you have built an ordinary LMS with extra steps.
D

Definition of done

Applies to every phase. A phase is not finished until all of these are true.

  • Every new tenant-scoped table has RLS enabled and forced, with a policy test
  • The isolation suite has a new case for every list endpoint added
  • Every write endpoint accepts an idempotency key and is safe to retry
  • Every state-changing action writes an audit entry with actor, before and after
  • Permissions tested per role, including the negative cases
  • Background jobs carry explicit tenant context and fail closed when it is absent
  • Migrations are additive first, with backfill and cleanup as separate releases
  • The phase is behind a feature flag with a tested rollback
  • The demo script runs end to end on staging with seeded data
  • Conscious gaps for the phase are written down and shared with pilot customers

Metrics to instrument from phase four onward

  • Median and p90 verification turnaround. The single health metric for the whole product.
  • Claims submitted per active member per month.
  • Return rate on claims, split by verifier. High variance means the rubrics are not doing their job.
  • Disagreement rate when two verifiers see the same evidence.
  • Share of verified assertions that reach expiry without renewal.
