MVP specification / v1 draft

A skills platform where a human signature is the source of truth

Learners study anywhere. The platform holds the skill map, decides who is allowed to confirm what, records the evidence, and pays out only against confirmations. Multi-tenant across separate organisations.

00

Overview and scope

Three commitments shape every decision in this document.

  • Content is not the product. A person can learn from YouTube, a book, or a colleague. The platform tracks skills, not course completions, so nothing depends on hosting or authoring material.
  • Verification is permission-based. Each organisation nominates who may confirm which skill at which level. A tech lead confirms backend skills up to L4 in their own department and nothing else. That rule is data, not code.
  • Two-tier confidence. A self-claim and a verified assertion are separate records. Reports, promotions and rewards read only the verified tier.

C1

Tenancy and identity

Tenants are unrelated companies. A person is not owned by a tenant.

person(id, email UNIQUE, display_name, did, created_at)
tenant(id, slug UNIQUE, name, status, plan, accent_color, logo_url)
org_unit(id, tenant_id, parent_id, name, path LTREE)
membership(id, person_id, tenant_id, org_unit_id, job_profile_id,
           employee_ref, status, joined_at, ended_at)
           UNIQUE(person_id, tenant_id)
identity_provider(id, tenant_id, kind, issuer, client_id, domain_hint)

Backend

  • Every row outside person and tenant carries tenant_id. No exceptions, including join tables.
  • org_unit.path as a materialised path makes subtree scope checks a single index lookup, which C2 calls on every request.
  • Login resolves an email to a person, then lists their active memberships. One membership means straight in; two or more means a tenant picker.
  • Tenant provisioning is a single transaction: tenant row, root org unit, seeded role bundles, taxonomy overlay pointer, empty budget pool, signing keypair.
  • Ending a membership revokes sessions and hides the person from tenant reports, but never deletes their assertions. Verification history is the tenant's audit record.

Frontend

  • Tenant resolved from subdomain, falling back to a picker at /choose. Accent colour and logo load with the session so the shell never flashes unbranded.
  • The tenant name sits in the top bar permanently. People working across two organisations must never be uncertain which one they are acting in.
  • Org unit picker is a searchable tree, not a flat select. Ten thousand people in a flat list is unusable.
  • Invite flow accepts a CSV of email, org unit, job profile, and shows a dry-run diff before committing.
C2

Authorization

Roles get a person into the application. Authority lets them sign a specific claim. These are different systems.

capability(key)                        -- flat list, seeded, not tenant-editable
role(id, tenant_id, name, is_system)
role_capability(role_id, capability_key)
role_grant(id, tenant_id, principal_type, principal_id, role_id,
           scope_type, scope_id)      -- principal: person | group

verifier_authority(id, tenant_id, principal_type, principal_id,
  skill_id NULL, skill_group_id NULL, max_level,
  scope_org_unit_id, requires_quorum, can_delegate,
  valid_from, valid_to, granted_by, revoked_at)

Seeded capabilities

KeyHeld by
skill.claim.submitEveryone with a membership
skill.verifyVerifier role, gated further by authority
verifier.grantOrg admin only. Separate capability from everything else.
credential.revokeOrg admin only, always logged with a reason
taxonomy.edit, jobprofile.editL&D admin
reward.rule.edit, reward.budget.fundSplit deliberately: who sets rules is not who releases money
report.org.viewManager, scoped to their subtree
member.invite, member.offboardOrg admin

Backend

  • One function, can(actor, capability, resource), plus a bulk variant that returns a filter predicate for list endpoints. Nothing bypasses it.
  • Resolved capability set cached in Redis per session, invalidated on any role_grant or verifier_authority write.
  • Authority resolution is a single query: rows matching principal or their groups, where max_level >= requested, the skill matches directly or through skill_group, the learner's org path is inside scope_org_unit, and now falls inside the validity window.
  • Written in plain SQL rather than a policy engine. Auditors and new engineers both need to read it.
  • Every deny is logged with the failing check. "Permission denied" with no reason generates support tickets forever.

Frontend

  • Session response carries the capability set. The shell hides what cannot be done rather than showing a dead control.
  • Authority is shown positively on the verifier's own profile: which skills, up to which level, for which teams. People need to know the shape of their own mandate.
  • The grant screen is a matrix, not a form: principals down, skill groups across, level as the cell value. Bulk editing is the normal case.
  • Denied actions explain the missing piece and offer to request it, which creates an audit trail of who wanted what.
C3

Skill taxonomy and levels

A taxonomy classifies. A framework assesses. You need both, and they are different tables.

skill_domain(id, tenant_id NULL, name, sort)      -- NULL tenant = global
skill(id, tenant_id NULL, domain_id, name, slug,
      external_code, description, status, version)
skill_level(id, skill_id, level SMALLINT,          -- 1..5
      title, indicators TEXT[], evidence_kinds TEXT[],
      min_verifier_level, validity_months)
skill_edge(from_skill_id, to_skill_id, kind)       -- prerequisite | adjacent
tenant_skill_override(tenant_id, skill_id, name, status, hidden)

Backend

  • Global rows have tenant_id IS NULL. A tenant reading the taxonomy sees global rows left-joined to its overrides, which is copy-on-write: renaming a skill writes an override row and leaves the global untouched.
  • Skills are versioned, never mutated in place. An assertion records the skill_level version it was judged against, so rewriting a rubric next year does not retroactively change what someone was certified for.
  • skill_edge must stay acyclic. Reject the insert that would create a cycle rather than defending against it at read time in the roadmap engine.
  • Retiring a skill sets status and stops new claims. It never deletes, because assertions point at it.

Frontend

  • Browse by domain, search across everything. Search matters more than the tree once there are two hundred skills.
  • The level rubric is the primary content of a skill page. Learners read it to know what to aim at; verifiers read it while signing off. Same text, one source.
  • Prerequisites render as a small upstream graph on the skill page, not a full org-wide graph view. Nobody uses the big graph twice.
  • Admin editor is a spreadsheet-style grid with a live diff and a publish step. Editing a taxonomy row by row through modals is unusable at scale.
C4

Job profiles and grades

This is what turns "moving from one level to another" from a conversation into a diff.

track(id, tenant_id, name)                    -- Backend, Design, Sales
job_profile(id, tenant_id, track_id, grade SMALLINT, title, status)
profile_requirement(job_profile_id, skill_id, min_level,
      criticality)                            -- core | supporting | optional
readiness_snapshot(membership_id, job_profile_id, met, total,
      blocking_skill_ids, computed_at)

Backend

  • Readiness recomputes on any verified assertion write for that person, and nightly for everyone as a safety net. Cached in readiness_snapshot because managers open team views that would otherwise fan out into hundreds of queries.
  • Core requirements gate promotion; supporting ones show as advisory. Without that distinction every profile becomes a wall of blockers and people stop looking.
  • Promotion itself is deliberately not automated in the MVP. The platform says "requirements met" and an admin records the grade change. Auto-promotion invites gaming and removes the human judgement organisations actually want to keep.
  • Changing a profile's requirements is versioned. Anyone mid-roadmap stays on the version they started, with an opt-in to move.

Frontend

  • The learner's home screen is this diff, sorted by "closest to done". Not a course list.
  • Any grade in the track is explorable, including sideways ones, so someone can see the cost of switching from Backend L3 to Platform L3.
  • Each gap links straight to generating or opening a roadmap for that skill.
  • Manager view is a heatmap of subtree members against core requirements, with a filter for "one gap from promotion" — the single most requested report in every system of this kind.
C5

Resource catalog

Pointers to learning that lives elsewhere. The platform never hosts content in the MVP.

resource(id, tenant_id NULL, kind, title, url, provider,
      cost_cents, currency, duration_minutes, language,
      submitted_by, status, visibility)        -- global | tenant | private
resource_skill(resource_id, skill_id, level, confidence)
resource_rating(resource_id, membership_id, helpful BOOL,
      passed_level_after BOOL, comment, created_at)
resource_progress(membership_id, resource_id, state, updated_at)

Backend

  • URL normalisation and dedupe on insert, so the same Coursera link submitted by forty people is one record with forty ratings.
  • Fetch title and duration from Open Graph metadata on submission. Manual entry is a fallback, not the path.
  • Ranking for a skill level: helpful ratio weighted by how many raters later passed that level, then recency, then cost ascending. Free resources that work should outrank expensive ones that also work.
  • Progress states are saved, in_progress, done, self-reported and untrusted. They drive XP and nothing else.

Frontend

  • Resource lists always appear inside a skill level context, never as a standalone catalog to browse. The question is always "how do I get to L3", never "what courses exist".
  • An explicit "I learned this elsewhere" path that skips straight to claiming. Forcing people through the catalog to log a skill they already have is the fastest way to lose them.
  • Ratings ask two things after a level is verified: was it helpful, and did it prepare you. Two taps, asked at the moment the answer is known.
  • Cost and duration are shown on every row. People are choosing with their own evenings and often their own money.
C6

Roadmap engine

Given a verified profile and a target, produce an ordered plan that respects prerequisites.

roadmap(id, tenant_id, membership_id, target_job_profile_id,
      kind, status, generated_from_version, created_at, due_at)
      -- kind: generated | template | manual
milestone(id, roadmap_id, skill_id, target_level, sort,
      state, due_at, completed_at)
      -- state: locked | open | evidence_submitted | verified
roadmap_template(id, tenant_id, name, target_job_profile_id, spec JSONB)

Backend

  • Generation: diff verified assertions against requirements, expand each gap into intermediate levels if the person is two or more levels short, pull in unmet prerequisites transitively, topologically sort, then order ties by shortest estimated effort.
  • Milestones are locked until their prerequisites are verified. This is the one place the platform is prescriptive, and it is what makes the roadmap feel like a path rather than a list.
  • Regeneration is additive: it never deletes a milestone that has evidence attached. It appends and re-sorts.
  • Due dates are optional and default to absent. Imposed deadlines on self-directed learning produce abandonment, and the data on who is behind is worth less than the goodwill it costs.

Frontend

  • A vertical stepper, current milestone expanded, everything else collapsed to one line. The whole roadmap on one screen at a glance.
  • Locked milestones show why they are locked and link to the blocker. Never a grey row with no explanation.
  • Each open milestone shows the rubric for the target level, the accepted evidence, and a submit action. The person should never have to navigate elsewhere to act.
  • Progress is expressed in milestones verified out of total, plus XP. Percentage complete on a self-paced plan is a lie the interface should not tell.
C7

Assessment engine

When content lives anywhere, assessment integrity is the only thing that makes a claim worth anything.

item_bank(id, tenant_id NULL, skill_id, level, name, status)
item(id, bank_id, kind, stem, options JSONB, answer JSONB,
      difficulty, discrimination, status, retired_at)
attempt(id, tenant_id, membership_id, bank_id, skill_id, level,
      item_ids UUID[], started_at, submitted_at, score,
      passed, ip_hash, seed)
attempt_response(attempt_id, item_id, response JSONB, correct)
attempt_policy(bank_id, item_count, pass_pct, time_limit_s,
      cooldown_hours, max_attempts_per_quarter)

Backend

  • Items are drawn per attempt with a stored seed, stratified across difficulty so two attempts are comparable. The seed makes an attempt reproducible for dispute review.
  • Answers never leave the server. The client receives stems and options only, and scoring happens on submit.
  • Cooldown and quarterly attempt caps are enforced server-side against the policy row. A failed attempt is recorded, not discarded.
  • Item leakage is the main threat once tenants are separate companies. Mitigations in the MVP: per-tenant item subsets from a shared bank, per-item exposure counters, automatic retirement above a threshold, and answer-pattern similarity flags across attempts.
  • Above L2 the accepted evidence is an artifact or observation, so the engine handles upload, reviewer assignment and rubric scoring rather than auto-grading.

Frontend

  • One question per screen, visible progress and remaining time, no back navigation after answering. Autosave every response so a dropped connection does not void an attempt.
  • Result screen shows pass or fail, the threshold, per-domain breakdown, and the next action. It never shows which specific items were wrong, because that is how a bank drains.
  • Cooldown is stated as a date and time, not "try again later".
  • Artifact submission accepts files plus a link and a short written rationale against the rubric. The rationale is what a reviewer actually reads first.
C8

Evidence and verification

The core of the product. Everything else exists to feed this state machine and consume its output.

skill_claim(id, tenant_id, membership_id, skill_id, target_level,
      state, rubric_version, submitted_at, decided_at)

evidence(id, tenant_id, claim_id, kind, attempt_id NULL,
      artifact_url NULL, external_credential_id NULL,
      note, added_by, created_at)
      -- kind: assessment | artifact | observation | endorsement | external_cert

verification(id, tenant_id, claim_id, verifier_membership_id,
      decision, rubric_scores JSONB, comment,
      authority_id, policy_version, decided_at)
      -- decision: approve | return | reject

skill_assertion(id, tenant_id, membership_id, skill_id, level,
      claim_id, verified_at, valid_until, revoked_at,
      revoked_reason, credential_id)

Routing and the sign-off gate

On submit, the router finds every principal whose verifier_authority covers this skill, this level and this learner's org unit, minus anyone excluded by conflict rules. If requires_quorum is set for the level, the claim needs that many independent approvals before an assertion is written.

Backend

  • Every decision stores the authority row used and the policy version evaluated. A year later you can answer "under what rule was this allowed" without guessing.
  • Conflict rules in the MVP: not self, not a reciprocal pair inside the last 90 days, and optionally not the learner's direct manager for levels above a configured threshold.
  • SLA timer per level. On breach, escalate up the authority chain; on second breach, notify the org admin. Unreviewed claims are the failure mode that kills these systems, so the escalation is not optional.
  • Writing an assertion is one transaction that also computes valid_until from the level's validity_months, enqueues credential issuance, enqueues reward postings, and recomputes readiness.
  • Revocation writes revoked_at, publishes to the credential status list, and emits a reversal transaction to the rewards ledger. Nothing is deleted.
  • The audit log is append-only and outside module reach: claim id, actor, action, before and after state, request id, timestamp.

Frontend

  • Learner side: one submission screen per milestone, showing accepted evidence kinds for that level, what has been attached, and what is still missing before submit is enabled.
  • Verifier queue is the single most important screen in the product. Sorted by SLA risk, filterable by skill, with the rubric and all evidence on one page and approve, return or reject as three primary actions.
  • Approval requires a rubric score per indicator plus a comment. A bare approve button produces worthless records and inflated levels.
  • Bulk approve exists only for checklist-style skills where the tenant has marked it allowed, and it still records per-person rubric defaults.
  • Verifier workload is visible to the verifier: pending count, median turnaround, and how many they have signed this quarter. Reviewing is unpaid work and needs to feel acknowledged.
  • Mobile matters here more than anywhere else. Tech leads approve from a phone between meetings.
C9

Credentials

Open Badges 3.0, signed per tenant, verifiable by anyone without an account.

issuer_key(tenant_id, did, public_jwk, kms_key_ref,
      created_at, rotated_at)
credential(id, tenant_id, assertion_id, subject_person_id,
      payload JSONB, proof JSONB, public_slug UNIQUE,
      issued_at, expires_at, status)
      -- status: active | expired | revoked | superseded
status_list(tenant_id, list_index, bitstring, published_at)

Backend

  • Issuer identity as did:web served from the tenant's own path, so the key is discoverable without a registry. Private keys live in a KMS and are never in the application database.
  • Payload includes the skill, the level, the rubric version it was judged against, the verifier's role rather than their name, the evidence kinds used, and the expiry. Alignment fields point at the taxonomy so an external reader can resolve what L3 means.
  • Revocation flips a bit in a published status list rather than rewriting credentials. Verifiers check signature first, status list second.
  • Recertification supersedes rather than replaces: the old credential stays verifiable and marked superseded, with a pointer to its successor. Career history should be readable.
  • Key rotation keeps old public keys resolvable indefinitely. Rotating a key must never invalidate history.

Frontend

  • Public verify page is server-rendered, no auth, fast, and readable on a phone: who, what skill at what level, when, by which organisation, what evidence type, valid until, and the signature check result.
  • It shows the rubric for that level in plain language. A hiring manager who does not know your framework needs to understand what was certified.
  • Share actions produce a link and a LinkedIn-ready payload. The badge image is secondary to the link.
  • The learner's wallet lists all credentials across every tenant they have belonged to, with expiry warnings ahead of time.
C10

Rewards ledger

Two currencies. XP is free and mint-only. Coins are conserved and come out of a funded budget.

xp_event(id, tenant_id, membership_id, source_event_id,
      rule_id, amount, created_at)              -- single entry, mint only

reward_account(id, tenant_id, kind, owner_id)   -- budget_pool|wallet|escrow|sink
reward_txn(id, tenant_id, kind, source_event_id,
      idempotency_key UNIQUE, actor_id, memo,
      reverses_txn_id, created_at)
reward_posting(id, tenant_id, txn_id, account_id, amount_signed)
      -- CHECK: sum(amount_signed) per txn_id = 0

earning_rule(id, tenant_id, trigger, condition JSONB, xp, coins,
      per_period_cap, cooldown_hours, version, active)
reward_item(id, tenant_id, kind, name, coin_price, stock, active)
redemption(id, tenant_id, membership_id, reward_item_id,
      state, txn_reserve_id, txn_settle_id, fulfilled_ref)

Backend

  • No balance column anywhere. Balance is a sum over postings with a nightly materialised snapshot for list views.
  • idempotency_key derives from the source event and rule id, so a replayed webhook or a re-run rule collides instead of paying twice.
  • Coins mint only from verified assertions, level satisfaction, verification work performed, and mentoring. XP can respond to softer signals like finishing a resource.
  • Minting fails loudly when the budget pool is empty rather than going negative. The admin sees a blocked-mint queue.
  • Redemption is reserve, fulfil, settle, with rollback on vendor failure. Skipping escrow either eats coins or gives them away free depending on the failure direction.
  • Anomaly job flags reciprocal verifier pairs, sub-minute approvals, and any verifier accounting for an outsized share of a department's coins.
  • Postings record the earning_rule version. Someone will ask why the same skill paid double last quarter.

Frontend

  • Wallet screen shows coin balance, XP total, and a plain transaction history. Every line names the assertion or event that caused it, linked.
  • The catalog leads with non-cash items where possible: conference budget, a stretch assignment, assessor status, an extra learning day. These cost less and motivate senior people more.
  • No global leaderboard. Cohort standing as a percentile band, opt-in, plus personal-best framing. Ranked lists demoralise everyone below the top.
  • XP naming is a tenant setting, because some organisations find game vocabulary infantilising for senior staff.
  • Admin sees accrued liability, burn against budget, and a per-person per-financial-year redeemed total for payroll, since redeemable rewards are generally taxable perquisites.

Events and analytics

One append-only stream feeds rules, reports and the audit trail. Reports never touch the transactional tables.

event(id BIGSERIAL, tenant_id, membership_id NULL, actor_id NULL,
      verb, object_type, object_id, context JSONB,
      request_id, occurred_at)
      -- verb: resource.completed | attempt.passed | claim.submitted
      --       claim.verified | claim.returned | assertion.expired
      --       credential.issued | credential.revoked | coins.minted

audit_log(id BIGSERIAL, tenant_id, actor_id, action,

Reports that ship in the MVP

ReportAnswers
Skill coverageHow many people hold each skill at each level, per org unit
Gap against profilesWhich core requirements are unmet across a team, ranked by count

C12

Automation rules

A small trigger, condition, action engine. Its job is to stop admins from doing repetitive work by hand.

rule(id, tenant_id, name, trigger_verb, condition JSONB,
      actions JSONB, active, version, created_by)
rule_run(id, rule_id, event_id, status, result JSONB, ran_at)
notification(id, tenant_id, membership_id, kind, payload JSONB,
      channel, sent_at, read_at)

Backend

  • Rules evaluate off the event stream in a worker, not inline in the request. A slow rule must never slow down a verification approval.
  • Every run is recorded in rule_run with its result, keyed on the event id so a replay is idempotent.
  • Scheduled triggers as well as event ones: expiry at 90, 30 and 7 days, stalled roadmap after 30 days of no activity, weekly verifier queue digest.
  • Actions available in the MVP: assign a roadmap or template, send a notification, mint XP or coins, grant a temporary authority delegation, flag for admin review.
  • Notification batching per person per day by default. A rule engine that emails on every event trains people to filter you out.

Frontend

  • Rules list with plain-language summaries: "when a person joins Backend, assign the L2 roadmap". Read the intent without opening it.
  • Editor is a guided form with a dry-run that reports how many people the rule would have affected over the last 30 days. Nobody should activate a rule blind.
  • Notification preferences per person, per kind, with email and in-app as the MVP channels.
C13

Admin console

Tenant self-service. If an organisation needs your team to configure their skill framework, the product does not scale.

Onboarding a new tenant

  • Create tenant, invite the first admin, done. Everything else is optional and has a working default.
  • Start from a seeded taxonomy and job ladder for their industry, then edit. A blank framework is where every pilot dies.
  • CSV import for members with org unit and grade, dry-run diff before commit.
  • A guided checklist that unlocks features as prerequisites are met: taxonomy published, one job profile defined, at least one verifier granted authority. Rewards stay locked until a budget is funded.
F

Frontend architecture

Three surfaces, one shell. Most people are two of the three roles at once.

Stack and conventions

  • React with a file-based router, server-side rendering for the public credential verify page and nothing else. That page must be fast and crawlable; everything else is behind auth.
  • Server state through a query cache keyed by tenant plus resource. Never cache across a tenant switch, and clear on switch.
  • The session payload carries capabilities, tenant theme and the org scope. One request, cached, drives all conditional rendering.
  • Design tokens from CSS custom properties so tenant accent and logo apply without a rebuild.
  • Forms: optimistic on cheap toggles, pessimistic with an explicit confirmation on anything that writes to the ledger or the assertion table. Verification approvals are not optimistic.
  • Empty states carry the next action. A learner with no roadmap sees "pick a target grade", not an illustration.
  • Accessibility floor: keyboard reachable review queue, visible focus, no colour-only status. Verified, expired and revoked need shape or text as well as colour.

Screens worth prototyping first

  1. Verifier review queue and evidence detail. If this is not fast and pleasant, nothing else matters.
  2. Learner roadmap with the gap diff. This is what makes people log in.
  3. Authority grant matrix. This is what makes an admin trust the platform.
  4. Public credential verify page. This is what makes the credential worth having.
B

Backend architecture

A modular monolith. The boundaries will be wrong for the first year, and moving a module is cheaper than moving a service.

Stack

LayerChoice and reason
RuntimeNode with TypeScript, or Go if the team prefers it. Either is fine; the schema and the permission model are the hard parts, not the language.
DatabasePostgres. Row-level security, LTREE for org paths, JSONB for rubrics and payloads, and one place to enforce the ledger invariant.
CacheRedis for resolved capabilities, session, rate limits, item exposure counters.
QueueOne durable queue with per-tenant partitioning. Credential signing, rule evaluation, report generation, notification batching.
Object storageS3-compatible, per-tenant key prefix, signed URLs with short expiry, server-side encryption. Evidence artifacts are sensitive.
KeysKMS for tenant signing keys. Never in the application database.

Module boundaries

Each module owns its tables and exposes a service interface. Cross-module reads go through that interface, never a raw join, because that is what keeps a later extraction possible.

identity     tenancy, person, membership, org_unit, idp
authz        capability, role, grant, verifier_authority, can()
skills       domain, skill, skill_level, edge, override
profiles     track, job_profile, requirement, readiness
catalog      resource, mapping, rating, progress
roadmaps     roadmap, milestone, template, generation
assessment   bank, item, attempt, policy
verify       claim, evidence, verification, assertion, routing, SLA
credentials  issuer_key, credential, status_list, verify endpoint
rewards      xp, accounts, txn, posting, earning_rule, redemption
events       event, audit_log, read models, reports
automation   rule, rule_run, notification

Non-obvious rules worth writing down

  • Only verify may write skill_assertion. Only rewards may write postings. Enforced by database grants per module role, not by code review.
  • Every write endpoint takes an idempotency key. Mobile clients on poor connections retry, and a duplicate approval is a real incident.
  • Background jobs carry the tenant context explicitly. A worker with no tenant set must fail rather than run unscoped.
  • Migrations run online, additive first, with a backfill job and a separate cleanup release. A multi-tenant table lock at business hours affects every customer at once.
S

Isolation and audit

Tenants are competing companies. A cross-tenant read is a breach, not a bug.

ALTER TABLE skill_claim ENABLE ROW LEVEL SECURITY;
ALTER TABLE skill_claim FORCE  ROW LEVEL SECURITY;   -- or the owner bypasses

CREATE POLICY tenant_isolation ON skill_claim
  USING (tenant_id = current_setting('app.tenant_id')::uuid);

-- set once per checked-out connection, before any statement
SET LOCAL app.tenant_id = $1;
  • FORCE ROW LEVEL SECURITY is the line teams forget. Without it the application's own database user, being the table owner, ignores every policy.
  • Shared schema with a tenant_id column is the right default at this stage. Keep a migration path to a dedicated database per tenant for the first enterprise buyer who demands it, and never write code that assumes a single connection string.
  • Integration tests assert isolation directly: seed two tenants, run every list endpoint as tenant A, assert zero rows from tenant B. This suite grows with every endpoint and is not optional.
  • A nightly job samples each tenant-scoped table for rows reachable under the wrong context and alerts on any hit.
  • Platform staff impersonation exists, is time-boxed, requires a stated reason, notifies the tenant admin, and is logged separately from ordinary audit entries.
  • Per-tenant export and delete built in phase one. Retrofitting deletion across twelve modules is far worse than designing it now, and India's DPDP Act plus GDPR both require it.
  • Evidence artifacts can contain client-confidential work product. Retention policy per tenant, default two years past assertion expiry, with the artifact deletable while the assertion and its rubric scores survive.
P

Build order

The sequence matters because each stage makes the next one demonstrable to a pilot customer.

StageShipsProvable claim at the end
1. SpineC1 tenancy and identity, C2 authorization, audit log, isolation test suiteTwo organisations can coexist and nobody can see across.
2. MapC3 taxonomy with rubrics, C4 job profiles and readiness diff, admin editorsAn organisation can describe its own skill framework and grades without your help.
3. LoopC8 verification end to end, C7 basic assessment, C5 resource pointers, C6 roadmapsA person can claim a level, a tech lead can sign it off, and the gap closes. This is the product.
4. ProofC9 credentials with signing, public verify page, expiry and recertificationA credential holds up outside the organisation that issued it.
5. MotionC10 rewards ledger, C12 automation, C11 reportsThe loop runs without an admin pushing it, and finance can see the cost.
Stage 3 is the only stage that cannot be cut down. If time pressure arrives, ship a smaller taxonomy, fewer reports and no rewards, but never a weaker verification workflow. That is the whole differentiator.

What to validate with the first pilot

  • Do verifiers actually review? Median turnaround under a week is the health metric. If the queue rots, the rest of the system is decoration.
  • Does the level rubric survive contact with real judgement, or do two verifiers read L3 differently? Disagreement rate on the same evidence is worth measuring deliberately.
  • Do learners submit claims for skills they already have, or only for new learning? Both are fine, but they imply very different roadmap defaults.
  • Does anyone use the resource catalog, or do people just learn elsewhere and come back to claim? If it is the latter, cut the catalog and invest in assessment.
X

Future scope

Ordered by how much each one depends on the MVP being real first.

Near term — once the loop runs

  • Standards ingestion. Import ESCO or SFIA as the global taxonomy so a new tenant starts from thousands of defined skills rather than a blank page. SFIA's seven responsibility levels map cleanly onto a level scale if you plan the mapping table early.
  • External credential auto-verification. When an uploaded certificate is an Open Badge, verify the signature and mark it machine-verified instead of waiting for a human. This is the highest-leverage reduction in verifier load available.
  • HRIS and SCIM sync. Job code, manager and org unit flowing in automatically removes the largest ongoing admin burden and makes automation rules reliable.
  • Verifier calibration. Route the same anonymised evidence to several verifiers periodically and report the spread. This is how you keep L4 meaning the same thing in two departments.
  • Appeals workflow. Necessary the moment verified levels influence pay. A rejected claim needs a documented route to a second opinion.

Medium term — new capability

  • Skill inference from work. Read pull requests, tickets and documents to propose claims a person could make. Proposals only, never automatic assertions.
  • Internal gig and mentor marketplace. Match verified skills to short assignments and mentoring requests. This is the single strongest non-cash reward you can offer, and it also generates observation evidence as a side effect.
  • Practical assessment. Code sandbox, scenario simulation, structured observation forms on mobile for frontline and clinical work. Each unlocks a whole industry vertical.
  • Cross-tenant recognition. Let one organisation choose to accept another's verified assertions under a published trust policy. The reason to build the credential layer properly is so this becomes possible later.
  • Content standards adapters. SCORM and cmi5 import, LTI 1.3 launch, an xAPI endpoint. Only build these when a specific deal needs them, and prefer cmi5 over SCORM for anything new.
  • Warehouse and embedded analytics. Move reporting off the replica once tenants ask for their own dashboards and custom cuts.

Longer term — platform

  • Agent-facing API over MCP. Expose read tools such as gap lookup, roadmap status and verifier queue so an assistant can answer "what am I missing for L4" in a chat client. Keep write access narrow: submitting a claim is plausible, approving one should stay in the interface where the rubric is visible.
  • Dedicated database tier. A silo option for regulated or white-label buyers, with the pooled tier remaining the default. Design the tenant router now so this is a configuration change rather than a rewrite.
  • Learner-owned wallet. A portable credential store the person controls independently of any employer, which is where the verifiable credentials model eventually leads.
  • Workforce planning. Model capability against a future org design and cost the training path. This is the report a CHRO will pay for, and it needs several years of verified data to be worth anything.
  • Marketplace for assessments. Third parties author and maintain item banks and observation rubrics for a domain, with revenue share. Only viable once enough tenants share a taxonomy.

Deliberately out of scope, probably forever

  • Authoring and hosting course content. It is a different company with different economics, and the whole premise here is that content is abundant and trust is scarce.
  • Automatic promotion or pay decisions. The platform should produce defensible evidence and leave the decision with people. The moment an algorithm sets grades, every incentive in the system inverts.
  • Global public leaderboards. Cheap to build, corrosive to the culture that makes verification honest.
